Unvarnish on OWASP NodeGoat

NodeGoat is an OWASP training application that is insecure on purpose, so a review should find plenty. Below is a real run, command by command, with its output unedited apart from local paths, and the findings document it wrote.

Read the findings document PDF Markdown

The walkthrough

  1. Start an engagement

    An engagement is a folder that holds the tools under review and every artifact the run writes.

    $ unvarnish init nodegoat-review --client "Demo client" --consultant "Unvarnish demo"
Created engagement at ./nodegoat-review
Next: unvarnish add <name> --repo <url|path> from inside it.

  2. Let the dependency scanner look advisories up online

    osv-scanner runs offline by default, for air-gapped sites. For this public demo we let it query osv.dev, with one line in engagement.yaml:

    scanners:
  dependencies:
    offline: false

  3. Add the tool

    Unvarnish clones the repository with its full history, so the secrets scanner can search every commit and the git phase can measure who wrote what.

    $ unvarnish add nodegoat --repo https://github.com/OWASP/NodeGoat.git
Added nodegoat (repo) at tools/nodegoat/source
  commit c5cb68a7084e on master

  4. Run it

    This run had no model configured, so the four model phases were skipped and the findings document comes from the deterministic scanners alone. The whole run took about twelve seconds.

**Impact.** Anyone who can read this code or its history holds a working credential. Rotation is required regardless of whether the file is still present.

What this demo does not show

  • No model ran. With one configured, the same run adds model findings checked by the verifier, an executive summary, and the architecture and requirements documents.
  • One tool only, so there is no cross-tool comparison.
  • A first review, so there is no "Since the previous review" section; a follow-up run with --baseline adds one.
  • The run used gitleaks 8.30.1 and osv-scanner 2.7.1 from their release pages, and end-of-life dates fetched with unvarnish eol refresh before the run; without that data the end-of-life check is reported as not run. The Docker image bundles all three.
  • One medium finding is a heuristic: it lists route handlers with no authentication identifier nearby, and here it includes routes guarded by NodeGoat's isLoggedIn middleware. With a model configured, extraction is asked to confirm each one.
  • NodeGoat is meant to be insecure. These findings describe a training application, not a product anyone runs in production.
